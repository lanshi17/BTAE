# BTAE 产品需求文档（PRD）

## 1. 概述

BTAE 面向长期使用 AI Agent 开发软件的个人与团队，以轻量工程协议引擎 EPE 连接设计、契约、代码、测试和证据。首个产品目标是让开发者知道每次修改依据什么设计、影响哪些实体、经过哪些检查，以及当前结果能否作为完成依据。

本文定义产品问题、范围与发布条件；[SPEC](requirements/SPEC-BTAE.md) 定义对应的技术行为。当前均为草案，尚无产品实现或效果验证。

## 2. 相关角色

| 角色 | 责任 | 当前负责人 |
| --- | --- | --- |
| 项目发起人 / 产品负责人 | 确定范围、优先级与产品验收 | 项目维护者，具体人员待指定 |
| 架构与安全负责人 | 审核核心边界及高风险变更 | 待指定 |
| 开发者 / Developer Agent | 维护设计、实现与验证映射 | 按任务指定 |
| Reviewer / 维护者 | 评审设计、证据及例外 | 按权限指定 |
| CI / Agent 集成负责人 | 配置执行环境与强制门禁 | 待指定 |

角色可以由同一人承担；文档中的角色名不构成实际权限授予。

## 3. 背景与问题

Agent 能快速生成代码，但多轮修改容易遗失设计依据、破坏模块边界，或根据过时契约开发。现有文档与测试通常分散，维护者难以判断“测试曾通过”是否仍适用于当前代码。

单纯增加 Markdown 数量无法解决这些问题。按文件机械生成文档还会扩大同步成本。BTAE 以逻辑实体建立映射，用可执行检查发现明确偏差，用有版本关联的证据支持决策。

当前具备 Markdown、Git、AST、契约测试和 CI 等成熟基础，可以先实现本地、单仓库、Python 优先的工作流。对其他工具的借鉴见[参考资料](../architecture/references.md)；本文不依赖未经核实的研究数字证明市场或产品收益。

## 4. 产品目标与衡量

### 目标

让维护者在合并前发现设计映射失效、必需审批缺失、验证失败和证据过期；让 Agent 获取任务相关依据，减少凭旧上下文修改工程。

### 首版发布关键结果

以下是发布时必须验证的目标，不是现有成绩或对真实项目效果的承诺。

| 编号 | 发布目标 | 测量方式 |
| --- | --- | --- |
| KR-01 | MVP 验收矩阵中的必需正例与反例全部通过 | 固定样例、命令输出与独立断言 |
| KR-02 | 缺少必需设计、审批失配、必需测试失败及 stale 证据均阻断完成门禁 | 注入已知违规场景 |
| KR-03 | 相同输入重建得到相同规范化实体与关系内容 | 删除缓存后重建比较 |
| KR-04 | 样例任务可从设计定位实现、测试和有效证据，并反向定位设计 | 端到端人工与自动验收 |
| KR-05 | 初始化和检查不覆盖已有权威工件，不伪造审批或测试结果 | 冲突、失败和无提交仓库场景 |

真实收益在后续试点记录：回归缺陷、架构违规、维护时间、Token、检查耗时和误报率。尚无基线，不预设降低百分比；试点后再确定改进目标。

## 5. 用户与使用场景

| 用户 | 要完成的工作 | 主要限制 |
| --- | --- | --- |
| 个人开发者 | 用 Agent 连续迭代项目，保持设计与行为一致 | 不愿部署复杂平台，维护时间有限 |
| 团队维护者 | 审查变更依据、影响与验证证明 | 不能逐行信任 Agent 自述 |
| Developer Agent | 找到相关设计、契约和测试，按范围实现 | 上下文有限，可能使用过期信息 |
| 架构负责人 | 保持模块边界，区分合法演进与偏差 | 静态导入无法覆盖全部运行依赖 |
| 集成工程师 | 在 Hermes、Codex CLI、Claude Code 或 CI 接入统一协议 | 各宿主权限与工具能力不同 |

首版服务已使用 Git、愿意维护核心设计的单仓库 Python 项目。既有项目允许逐步登记治理范围；范围外实体必须标为未纳管，不能宣称已覆盖全仓库。

## 6. 用户价值

- 开发前获得直接相关的设计和依赖，减少盲目阅读与遗漏。
- 开发中明确公共契约、允许范围和所需审批，减少协作假设冲突。
- 开发后获得可定位、可判断新鲜度的验证记录，便于审查和回溯。
- 维护时同时查看预期架构与实际观测，支持解释演进原因。

差异化方向是实体追溯与证据治理的组合；是否优于单纯规格驱动仍是待检验假设。首版不以文档数量、图节点数量或代码覆盖率单一指标代表产品价值。

## 7. 产品方案

### 7.1 用户旅程

维护者初始化工程规则 → 注册核心实体与设计 → 创建任务并声明范围 → Agent 检查设计门禁 → 实现并执行检查 → 查看 Evidence 与诊断 → 修复失败项 → 维护者或 CI 判断能否完成。

失败信息应告诉用户具体实体、源位置、阻断原因及建议动作。JSON 供 Agent 消费，人类输出供本地开发与评审；两者表达同一结果。

### 7.2 产品需求

| ID | 需求 | 优先级 | MVP 范围 |
| --- | --- | --- | --- |
| PRD-001 | 安全初始化与工程状态检查 | P0 | 创建缺失配置，报告冲突和纳管范围 |
| PRD-002 | 稳定实体注册与文档解析 | P0 | ID、元数据、引用和来源校验 |
| PRD-003 | Python 代码解析与实现映射 | P0 | 类、函数、签名、导入及文件/符号定位 |
| PRD-004 | 可重建依赖图与架构规则 | P0 | 带来源的依赖、循环与禁止依赖检查 |
| PRD-005 | 设计先行门禁 | P0 | 缺设计、审批失配、权限或范围问题可阻断 |
| PRD-006 | 测试门禁 | P0 | 执行配置的检查，区分失败、故障与未执行 |
| PRD-007 | 验证证据与新鲜度 | P0 | 输入指纹、环境、结果、产物与有效性 |
| PRD-008 | 统一 CLI / CI 结果 | P0 | 人类/JSON 输出、退出码和综合检查 |
| PRD-009 | 四类任务入口 | P0 | 类型与最小任务记录；完整自动编排后续交付 |
| PRD-010 | 双向影响分析与上下文装配 | P1 | V0.3；MVP 只提供基础图与映射 |
| PRD-011 | 多 Agent 契约与写入冲突治理 | P2 | V1.0；MVP 只记录范围并报告已知冲突 |
| PRD-012 | 多宿主 Agent 适配 | P2 | V1.0 优先 Hermes，核心保持独立 |

P0 不要求建设图数据库、网页管理台、云服务、向量平台、通用多语言解析、运行 Trace 平台或由 LLM 自动裁决架构。首版允许本地调用，真正的强制执行依赖宿主权限和 CI 集成。

### 7.3 约束

工件留在仓库，设计采用 Markdown，机器约束采用结构化格式，生成索引可删除重建。初期按单进程、单仓库实现；所有执行结果可在没有外部 LLM 服务时产生。具体技术约束见 SPEC。

### 7.4 假设与风险

维护者愿意为核心实体维护设计和契约；相关检查覆盖关键行为；治理收益能够抵消额外操作成本。这些假设需要试点验证。

主要风险是过度设计、语义检查误报、动态依赖漏报、审批成为瓶颈、Agent 绕过工具和证据缺失。应通过渐进纳管、风险分级、显式未知状态和 CI 强制门禁降低风险。未实施宿主隔离时不得宣传“禁止所有未经授权写入”。

## 8. 发布计划与完成条件

V0.1 完成规格与机器工件定义；V0.2 交付八项 MVP 能力；V0.3 引入双向影响和上下文；V1.0 完善治理与宿主集成。工期需在 MVP 技术拆分后估算，不承诺未经评估的日期。

MVP 发布必须满足 KR-01 至 KR-05、SPEC 验收矩阵、可运行样例与使用说明，声明纳管范围和已知限制。Schema、Policy、Workflow、模板与实现未交付前，本 PRD 和 SPEC 只构成设计依据，不能宣称产品完成。
